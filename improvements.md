# Improvements for Embitious

This document outlines suggested improvements discovered during a comprehensive code review of the Embitious vector embedding service.

---

## 1. 🔴 Critical: Missing Health Check Dependency

**Suggestion:** Add the `quarkus-smallrye-health` dependency to `pom.xml`.

**Problem:** `src/main/kubernetes/kubernetes.yaml` configures liveness and readiness probes that hit `/q/health/live` and `/q/health/ready`. These endpoints are provided by the SmallRye Health extension, which is **not included** in the project dependencies. Without it, the health endpoints will return 404, causing Kubernetes to consider the pod unhealthy and never mark it as ready — preventing any traffic from reaching the service.

**Fix:** Add to `pom.xml`:
```xml
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-smallrye-health</artifactId>
</dependency>
```

Also consider adding a custom `HealthCheck` that verifies the embedding model is loaded and functional, rather than relying solely on the default "always healthy" response.

---

## 2. 🟡 High: Missing Observability — No Metrics

**Suggestion:** Add the `quarkus-micrometer` dependency and annotate key methods.

**Problem:** A production embedding service has no metrics at all. There is no visibility into:
- Request count and latency (p50/p99)
- Batch size distribution
- Error rate
- Predictor pool size / thread contention
- JVM memory (especially important with large models in heap)

**Fix:** Add Micrometer + Prometheus:
```xml
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-micrometer-registry-prometheus</artifactId>
</dependency>
```
Then annotate `EmbeddingResource.embed()` with `@Timed` and `@Counted`, and `EmbeddingService.embedBatch()` similarly. Expose a `/metrics` endpoint for Prometheus scraping. Also add the corresponding annotations in `kubernetes.yaml` for Prometheus auto-discovery.

---

## 3. 🟡 High: Kubernetes Probes Reference Non-Existent Endpoints

**Suggestion:** Update `kubernetes.yaml` with correct endpoints or add the missing extensions.

**Problem:** Same root cause as #1. The health check paths in the Kubernetes manifest won't work without the extension. Additionally:
- The `initialDelaySeconds: 30` may be too short if the model is large (e.g., `all-mpnet-base-v2` can take 30-60 seconds to download and load on first start). Consider increasing to 60-90 seconds or implementing a startup probe.
- Memory limits of 2Gi may be insufficient for larger models. Many sentence-transformers models require 1-2 GiB just for the model; with the JVM heap, 2Gi could cause OOM kills. Consider documenting model-specific resource requirements.
- The deployment uses a single replica — for a stateless service, HPA (HorizontalPodAutoscaler) configuration would be beneficial for production.

---

## 4. 🟡 High: Stale Duplicate in `bin/` Directory

**Suggestion:** Remove the `bin/` directory and add it to `.gitignore` if it's generated by an IDE/build tool.

**Problem:** The `bin/` directory contains a stale, older copy of the entire project (older `pom.xml`, older `Agent.md`, etc.). This is confusing and could lead to someone accidentally editing or referencing files in `bin/` instead of the real project root. It also bloats the repository and shows up in searches.

**Fix:** `rm -rf bin/` and add `/bin/` to `.gitignore`. Note that `/bin/` is already in `.gitignore` but the directory is tracked anyway because it was committed before the gitignore entry was added. Run `git rm --cached -r bin/` to untrack it.

---

## 5. 🟡 High: Swagger UI Exposed in Production

**Suggestion:** Make Swagger UI conditional on a profile or environment variable.

**Problem:** `quarkus.swagger-ui.always-include=true` in `application.properties` means the Swagger UI is always available, including in production deployments. This exposes API documentation publicly, which is a security concern.

**Fix:** Either:
- Remove `quarkus.swagger-ui.always-include=true` and use `%dev.quarkus.swagger-ui.always-include=true` for dev only, or
- Set `quarkus.swagger-ui.enable=false` by default and enable it via environment variable in non-prod environments.

---

## 6. 🟡 Medium: `predictorsToClose` Uses Redundant Synchronization

**Suggestion:** Remove the `synchronizedList` wrapper or simplify the cleanup logic.

**Problem:** In `EmbeddingService.java`, `predictorsToClose` is a `Collections.synchronizedList(new ArrayList<>())`, but all iteration over it happens inside an explicit `synchronized (predictorsToClose)` block. This double-synchronization is redundant and potentially confusing. A `ConcurrentLinkedDeque` or a simple `ArrayList` with the existing synchronized block would be cleaner.

**Additionally:** The `ThreadLocal` pattern means every thread that calls `embed()` or `embedBatch()` creates a predictor that lives until the service shuts down. In a Quarkus/JVM with a bounded thread pool this is fine (threads are long-lived), but if the pool ever grows (e.g., under load), the predictor list could grow. Consider using an object pool with a fixed maximum size (e.g., `GenericObjectPool` from Apache Commons Pool) or documenting the thread-pool dependency explicitly.

---

## 7. 🟡 Medium: No Bean Validation on DTOs

**Suggestion:** Use Jakarta Bean Validation annotations instead of manual null/blank checks.

**Problem:** `EmbeddingResource.embed()` manually validates that the request text is not null or blank. This is verbose and error-prone. Quarkus supports Jakarta Bean Validation natively with the `quarkus-hibernate-validator` extension.

**Fix:** Add `quarkus-hibernate-validator` and annotate the DTO:
```java
// EmbeddingRequest.java
@NotBlank(message = "Text must not be null or empty")
private String text;
```
Then use `@Valid` on the resource method parameter:
```java
public Response embed(@Valid EmbeddingRequest request) { ... }
```
The framework handles 400 responses automatically with proper error messages.

---

## 8. 🟡 Medium: No Timeout or Circuit Breaking

**Suggestion:** Add timeout protection for embedding computation and JMS message processing.

**Problem:** There is no timeout configured on the embedding computation or JMS message processing. A very long text or a model issue could cause a thread to block indefinitely. Also, if the JMS broker is unavailable at startup, the service silently swallows the exception and continues — there's no retry logic or circuit breaker.

**Fix:**
- Add a `@Timeout` annotation or use `CompletableFuture` with `orTimeout()` in the embedding service.
- Consider adding `quarkus-smallrye-fault-tolerance` for `@Timeout`, `@Retry`, and `@CircuitBreaker` annotations.
- For JMS, implement a reconnection strategy (e.g., schedule a periodic retry) rather than silently failing forever.

---

## 9. 🟡 Medium: Inconsistent Docker Base Images

**Suggestion:** Document when to use each Dockerfile, or consolidate.

**Problem:** There are four Dockerfiles (`Dockerfile.jvm`, `Dockerfile.legacy-jar`, `Dockerfile.native`, `Dockerfile.native-micro`) with no documentation about which to use. The JVM variants use Red Hat UBI 8 images, while the native-micro uses a Quarkus micro image. UBI 8 `openjdk-21-runtime:1.20` may not be the latest — UBI 9 is available and recommended for Java 21.

**Fix:** Add a comment block at the top of each Dockerfile explaining its purpose, or consolidate into a single multi-stage Dockerfile. Also consider upgrading to UBI 9 base images.

---

## 10. 🟡 Medium: No Structured Logging / Request Tracing

**Suggestion:** Add correlation IDs and structured logging.

**Problem:** The REST endpoint logs with `LOG.debugf` but doesn't include any request identifier or correlation ID. In production, tracing a request through logs is difficult. The JMS listener has a `requestId` from the batch request but doesn't propagate it to log messages.

**Fix:**
- Add a `quarkus-logging-json` extension for structured JSON logging in production.
- Generate or extract a correlation ID (e.g., from an `X-Request-ID` header) and add it to the MDC (Mapped Diagnostic Context).
- Add `quarkus-smallrye-opentracing` or `quarkus-opentelemetry` for distributed tracing between REST and JMS layers.

---

## 11. 🟢 Low: Test Organization — Integration Test in Unit Test Class

**Suggestion:** Rename or split `EmbeddingResourceTest`.

**Problem:** `EmbeddingResourceTest` runs with `@QuarkusTest`, which starts the full Quarkus context (including the real `EmbeddingService` with model loading). The test `testEmbedBatch()` directly calls `embeddingService.embedBatch()` — it is not actually testing the REST endpoint at all. This test belongs in `EmbeddingServiceTest` or a dedicated integration test class. It also fails if no model is downloaded, which contradicts the project's testing conventions that state tests "must not require a running broker or a downloaded model."

**Fix:** Move `testEmbedBatch()` to `EmbeddingServiceTest` and mock the predictor, or mark it with `@Disabled` by default and enable it only when a model is available. Use a `@Tag("integration")` for tests that require real infrastructure.

---

## 12. 🟢 Low: `error` Field in JSON Responses Could Be More Structured

**Suggestion:** Add an error code or error type field to error responses.

**Problem:** Both `ErrorResponse` (REST) and `BatchErrorResponse` (JMS) only contain a human-readable `error` string. This makes error handling on the client side fragile (clients must parse error strings). Adding an error code (e.g., `INVALID_INPUT`, `MODEL_ERROR`, `INTERNAL_ERROR`) would make client integrations more robust.

---

## 13. 🟢 Low: No Native Image Reflection Configuration

**Suggestion:** Add a `reflect-config.json` for GraalVM native image builds.

**Problem:** The `pom.xml` includes a `native` profile, and there are `Dockerfile.native` and `Dockerfile.native-micro`. However, there is no reflection configuration for DJL classes, Jackson serialization, or JMS message types. Native image builds will likely fail at runtime due to missing reflection metadata.

**Fix:** Add a `-H:ReflectionConfigurationFiles` option, or add `@RegisterForReflection` annotations on the DTOs and messaging POJOs. Consider testing the native build in CI.

---

## 14. 🟢 Low: CI Only Targets `master` Branch

**Suggestion:** Extend CI to run on more branches or use a more modern approach.

**Problem:** The GitHub Actions CI only runs on `master`. Feature branches and PRs to other branches won't be tested. This is a very minimal CI configuration and doesn't include:
- Dependency vulnerability scanning (Dependabot / Snyk)
- Native image build verification
- Docker image build verification
- Integration tests that spin up an Artemis broker (Testcontainers)

**Fix:** At minimum, trigger CI on all PRs regardless of target branch. Consider adding a matrix build for JVM + native, and adding Testcontainers for JMS integration tests.

---

## 15. 🟢 Low: `.vscode/` Directory Committed but Git-Ignored

**Suggestion:** Either remove `.vscode/` from `.gitignore` or remove it from the repository.

**Problem:** `.gitignore` lists `.vscode/` but `.vscode/settings.json` is committed to the repository. This is an inconsistency. If you want to share IDE settings, don't git-ignore the directory. If you don't, untrack it.
